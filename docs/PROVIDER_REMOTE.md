# Venue app remote candidate

## 2026-09-19 provider-only Game Day (2.3.5 candidate)

Game Day uses the selected provider only; URL playback remains in the separate Live Stream mode. Returning from Regular TV Board or a Live Game no longer loads the old saved Game Day URL. The box saves only the fixed provider identifier in its existing local pairing config. A validated same-provider playback path is kept in process memory for a mode round trip; query/hash values, authentication/account routes and foreign origins are excluded. That address is not sent to the backend or written to disk. A full restart restores the provider home, not a guaranteed channel. Re-pair/unpair clears the remembered selection. BrowserView destruction on exit remains to avoid hidden playback/CPU use.

Old saved_url and set_stream_url Game Day commands are rejected/ignored by 2.3.5; older installed clients retain their legacy contract until updated. The API fields remain for compatibility, while new dashboard/app controls no longer expose them. The Game Day web layout shows a provider placeholder; use the selected TV live remote for its actual picture. EverPass live playback remains unsupported on the Windows PWA; no working EverPass provider button is advertised.

Candidate tests cover provider/channel mode round trips, Live Games return, restart fallback, pairing reset, sensitive/foreign URL rejection and old command rejection. Signed packaging, exact-device physical acceptance and deployment/OTA must be separately recorded. Fleet offer remains 2.0.1.

Ordinary TV tokens alone are insufficient. The venue app chooses one device; existing venue-wide modes and legacy commands remain compatible.

## 2.3.4 recovery and explicit sound controls

A preview with no fresh picture for two seconds disables input; at eight seconds it invokes the existing bounded reconnect flow even if WebRTC still reports connected. Manual Reconnect remains available for an established session, but authorization/setup is serialized so repeated taps cannot consume a one-use mobile handoff twice. Existing expiry, two-attempt budget, privacy checks and no-input-replay rules remain.

The receiver coalesces hover movement and retains up to eight discrete commands, acknowledging rejected overflow explicitly. Mute and bounded integer volume (0–100) succeed only when a supported top-document/open-shadow media element matches the setting and Electron output mute matches. Missing/cross-origin-only players return unavailable. Commands do not resume playback or control Windows/TV volume. The viewer shows negative or missing acknowledgements independently of fresh pictures; its volume value is the requested setting, not live telemetry. Drag moves the pointer; tap clicks and may pause video.

Restart TV app is a separate, closed recovery action using the existing authenticated, enrolled, selected-device HTTP command channel. The server rejects volume/restart for versions older than 2.3.4. Restart schedules a single relaunch after two seconds to allow a receipt, discards updater command-line arguments, and rechecks the original pairing/key and update/presentation state. It retains the existing Chromium profile. A receipt means scheduled, not proof that restart completed; verify a subsequent heartbeat/picture. It cannot recover Windows, power or a fully offline process. App recovery is available outside Game Day; dashboard recovery is in selected-TV Game Day controls.

### ESPN TV-provider authentication candidate (2026-09-19)

A direct click on Hulu in ESPN's provider picker also remained on the picker on the physical 2.3.5 TV, independently of the phone remote. A normal browser reached Hulu sign-in. ESPN's rendered page uses `sp.auth.adobe.com/api/v2/ESPN/profiles`; Adobe's documented browser authentication handoff uses `/api/v2/authenticate/{serviceProvider}/{code}` followed by `/adobe-services/authenticate/saml`. The candidate permits only those ESPN authentication paths on the exact production host. Other Adobe routes, requestors, lookalike hosts, HTTP and arbitrary popups remain denied. Authentication pages remain excluded from live remote capture/control. This is a candidate fix, not a verified physical sign-in success.
